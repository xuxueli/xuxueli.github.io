### 1、引言：上下文的三重困境

大模型是无状态的。每一次推理，它看到的只有这一刻被塞进上下文窗口的那点 token；窗口之外的历史，无论多重要，都等于不存在。

于是 Agent 的工程质量，很大程度上取决于一件朴素的事：**每一轮，往窗口里放什么**。放少了，模型失忆、答非所问；放多了，窗口装不下、成本飙升；放得不对，关键信息被噪声淹没，模型反而更笨。

这就是上下文的三重困境：

- **装不下**：历史消息、工具结果、文件内容不断累积，迟早撞上模型窗口上限；
- **被淹没**：上下文越长，模型对中段信息的注意力越弱，出现"lost in the middle"与"context rot"；
- **记不准**：为了装下而做摘要，摘要又可能丢约束、漂移甚至编造。

很多团队的第一反应是"换个更大窗口的模型"。但窗口变大只是把问题推迟：成本更高、延迟更大、注意力更分散，而且历史仍会无限增长。真正要解决的，是**上下文的管理机制**，而不是窗口的物理大小。

本文沿用"先建坐标系、再看业界、最后落到工程"的思路，把这件事拆成三层：

- **会话（Session）**：上下文存在哪里、以什么结构存在；
- **压缩（Compaction）**：超限时如何有损地收敛；
- **上下文工程（Context Engineering）**：每一轮如何检索、组织、装配。

一句话概括三者关系：**会话负责"记住什么"，压缩负责"忘掉什么"，上下文工程负责"这一刻看什么"**。

### 2、坐标系：一条生命周期，五种压缩策略

#### 2.1、纵轴：上下文的生命周期

要设计上下文系统，先要看清一条消息从产生到被模型消费，中间经历了什么：

```
上下文生命周期（纵轴）
┌──────────────────────────────────────────────────────────────┐
│ ① 产生   用户输入 / 模型回复 / 思考过程 / 工具调用与结果      │
├──────────────────────────────────────────────────────────────┤
│ ② 存储   会话消息落库；线性消息表 或 会话树                   │
├──────────────────────────────────────────────────────────────┤
│ ③ 压缩   触发判定 → 选取增量 → 摘要 / 截断 / 卸载 → 推进游标  │
├──────────────────────────────────────────────────────────────┤
│ ④ 装配   系统指令 + 记忆 + 摘要 + 增量历史 + 工具 + 检索结果  │
├──────────────────────────────────────────────────────────────┤
│ ⑤ 消费   按 token 预算裁剪后送入模型，生成下一轮              │
└──────────────────────────────────────────────────────────────┘
```

这条链上有两个容易被混淆的概念：

- **存储的历史 ≠ 发送的历史**。数据库里可以保留全部消息，但每一轮真正送给模型的，只是经过筛选、压缩、装配后的一个"切片"；
- **压缩 ≠ 删除**。成熟的实现通常只改变"请求视图"，原始消息仍然保留，以便审计、回退和重新压缩。

把这两点想清楚，很多设计分歧就自然消解了。

#### 2.2、横轴：五种压缩策略

面对超限，业界并不是只有"摘要"一种答案。按信息形态与代价，可以收敛为五种策略：

| 策略 | 做法 | 信息保真 | 成本 | 延迟 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| **截断** Truncation | 丢弃最旧消息、裁剪超长工具输出 | 低 | 极低 | 无 | 兜底、工具结果治理 |
| **摘要** Summarization | 调模型把历史压成结构化摘要 | 中 | 中 | 中 | 通用会话压缩 |
| **检索** Retrieval | 原文落外部存储，按需召回 Top-K | 高（命中时） | 中 | 中 | 知识库、长期记忆 |
| **卸载** Offload | 大结果写入文件/对象存储，上下文只留引用 | 高 | 低 | 低 | 编码 Agent 的日志、文件 |
| **结构化状态** Structured State | 把任务状态提炼成 todo / plan / 变量 | 高（任务维度） | 低 | 低 | 长任务、多步执行 |

它们不是互斥的，而是可以叠加。一个成熟的 Agent 往往同时使用：**结构化状态承载任务骨架，摘要承载会话脉络，检索承载外部知识，卸载承载大块工具结果，截断作为最后兜底**。

#### 2.3、预算公式：什么时候必须压

无论用哪种策略，触发点都来自同一个预算模型：

```
可用历史预算
  = 模型窗口
  - 系统指令与工具定义（固定开销）
  - 长期记忆 / 技能索引 / 检索上下文
  - 输出预留（max_tokens）
  - 安全边际（防止估算误差）
```

当"已用 token / 窗口上限"超过阈值（常见 80%），或历史轮次超过上限，或摘要根本不存在时，就需要压缩。

这里有个常被忽略的取舍：**压得太早，浪费一次模型调用，还丢了本可以保留的细节；压得太晚，可能已经超出窗口，请求直接失败**。所以阈值通常不是单一指标，而是"使用率 + 轮次 + 是否存在摘要"的组合条件。

> 压缩的本质是**投影**，不是备份。摘要是历史在有限字数下的一次有损投影；理解这一点，才不会对摘要提出"什么都不能丢"的苛求。

### 3、业界对照：四种典型取舍

不同 Agent 产品对"会话"与"压缩"的建模差异很大，但底层思路高度一致：**存储保留全量，请求只看切片**。

| 维度 | Claude Code | OpenCode | Pi | Letta / MemGPT |
| --- | --- | --- | --- | --- |
| 会话模型 | 会话 + 消息历史 | 会话 + 消息 + 快照/回退 | **会话树**，消息为节点 | OS 式记忆分层 |
| 压缩触发 | 接近上限自动压缩，支持 `/compact` | 原生 / 摘要两种压缩模式 | 历史超窗口时插入摘要条目 | 记忆换入换出 |
| 压缩产物 | 摘要 + 近期消息 | 压缩 Agent 生成摘要 | 摘要条目替换更早消息 | 核心/召回/归档三层 |
| 原文保留 | 保留 | 保留，可回退 | **保留在会话树中** | 归档存储保留 |
| 特色 | 产品化、低门槛 | 隐藏 compaction Agent、插件钩子 | 分支/Fork 与 JSONL 持久化 | 记忆自管理 |

几个值得注意的细节：

- **Claude Code** 把压缩做成了产品默认能力：用户几乎不需要理解 token 预算，接近上限时自动摘要，同时保留近期消息，也提供 `/compact` 让用户主动整理；
- **OpenCode** 把压缩做成可插拔的运行时能力，存在隐藏的 `compaction` Agent，并允许插件在 `context` / `compaction` 等钩子上介入；会话快照与回退则保证了"压缩后仍可回到过去"；
- **Pi** 的会话是一棵树，压缩只是在活动分支上插入一个摘要节点，被替换的原始消息仍然留在树里，因此 Fork、回退、重新压缩都不会丢历史；
- **Letta / MemGPT** 走得更远，直接把上下文窗口类比成 RAM，把召回与归档当成磁盘，通过换入换出维持一个"看似无限"的记忆。

这些实现的共同点是：**压缩改变的是"这一轮请求看到什么"，而不是"系统还记得什么"**。这条原则，是后面所有工程细节的基础。

### 4、会话：上下文的载体

#### 4.1、消息模型：展示态与模型态要分开

一条会话消息，远比"role + content"复杂。工程上通常要记录：

```
SessionMsg / desk_message
  id          消息ID（会话内自增，决定顺序）
  sessionId   会话ID
  turnId      轮次ID（同一次用户请求产生的消息归为一轮）
  role        user / assistant / tool
  content     正文
  reasoning   思考过程（推理模型 reasoning_content）
  data        原始消息 JSON（用于运行时重建）
  source      来源（常规 / runtime:* 注入）
  status      生成中 / 完成 / 失败
  addTime     时间
```

为什么要分这么细？因为"给人看"和"给模型看"是两种需求：

- **展示态**需要思考过程、工具调用状态、耗时、折叠面板；
- **模型态**只需要对当前任务有用的信息，thinking 与冗长的工具结果往往是噪声。

很多上下文膨胀，不是因为用户话多，而是因为**把展示态原样塞进了模型态**。把两者分开，是上下文工程的第一道闸门。

#### 4.2、线性消息表 vs 会话树

会话的存储结构，直接决定了压缩与回退的难度。

**线性消息表**（多数产品的默认选择）：

```
session
  ├─ msg#1 user
  ├─ msg#2 assistant
  ├─ msg#3 tool
  └─ msg#4 assistant
```

优点是简单、易分页、易按游标增量读取；缺点是 Fork、分支、回退支持弱，一旦要"从中间某条消息重新开始"，只能复制会话或截断历史。

**会话树**（Pi 等采用）：

```
            ┌─ msg#2a ─ msg#3a   ← 分支 A（活动分支）
msg#1 ──────┤
            └─ msg#2b ─ msg#3b   ← 分支 B（保留但不参与本轮）
```

每条消息指向父节点，从根到当前节点的路径就是**活动分支**，也是本轮请求的历史来源。Fork、Clone、回退都只是移动"当前节点"，历史不被删除。

树模型的代价是存储与查询更复杂，压缩也要回答"压哪条分支"；但它带来一个非常重要的能力：**压缩是可回退的**。如果摘要质量不佳，可以回到压缩前的节点重新生成，而不是面对一份已被覆盖的历史束手无策。

#### 4.3、会话不是上下文

需要再次强调：会话是**持久化的全量历史**，上下文是**这一轮请求的切片**。

两者之间至少隔着四道处理：

1. 只取活动分支（树模型）；
2. 只取摘要覆盖点之后的消息（增量）；
3. 过滤 thinking、工具原始结果等低密度内容；
4. 按 token 预算做最终裁剪。

把"会话"当成"上下文"直接全量拼接，是很多 Agent 在长对话中变慢、变贵、变笨的根源。

### 5、压缩：把历史投影成状态

#### 5.1、触发：四个条件，各有取舍

常见的触发条件有四类：

- **无摘要**：会话第一次压缩，必须建立基线；
- **使用率阈值**：已用 token 超过窗口的 80% 左右，最贴近"容量"本身；
- **轮次阈值**：距上次摘要后真实用户轮次超过 20 轮，防止"窗口没满但话题已经飘远"；
- **手动触发**：用户或开发者通过 `/compact` 主动整理。

工程上通常取"或"的关系：任一命中就压。这样既能兜住容量，也能兜住语义漂移。

但要注意两个坑：

- **把工具调用轮次也算进"用户轮次"**，会导致压缩过于频繁；
- **在模型正在生成时触发压缩**，可能造成当前轮上下文被替换，出现"答到一半失忆"。正确做法是**每轮结束后异步触发，下一轮生效**。

#### 5.2、输入：只压"高信号密度"的部分

压缩的输入不应该等于全部历史。一个比较稳妥的选取方式是：

```
压缩输入 = 旧摘要 + 上次摘要之后的增量转录
增量转录 = 只取 user / assistant 正文
          排除 thinking、工具调用参数、工具原始结果
          超长时从最旧处截断（如上限 60k 字符）
```

为什么排除 thinking 和工具结果？

- thinking 是模型的中间草稿，复述价值低，且容易把错误推理固化进摘要；
- 工具结果往往体积巨大、重复度高，真正有价值的是"结论"，不是"原始输出"。

这一步的本质，是在调用模型之前先做一次**廉价的信息筛选**，把宝贵的摘要预算留给决策、约束与进展。

#### 5.3、输出：用固定 schema 对抗摘要漂移

自由发挥的摘要，十次有八次格式不同、重点漂移。工程上更可靠的做法，是给摘要一个**固定骨架**：

```
## 背景与约束
## 目标
## 关键决策
## 进展与产物
## 待办与风险
```

它的好处很直接：

- **稳定**：每次输出结构一致，便于程序解析、比对与合并；
- **可读**：人和模型都能快速定位；
- **可控**：定长截断（如 2000 字符）时，知道哪些章节该优先保留；
- **可演进**：后续要加"未解决问题""关键文件"等章节，只需扩展 schema。

对应地，提示词要明确要求：合并旧摘要与新对话、删除重复与过时信息、不得编造、无内容章节写"暂无"。

#### 5.4、游标：增量压缩的关键

如果每次压缩都重读全量历史，成本会随会话长度线性增长。解决办法是**游标（watermark）**：

```
消息序列（时间正序）
  ... [id=100] [id=101] [id=102] [id=103] ...
                    ▲
        summary_last_message_id = 101
                    └──────────┬──────────┘
                     本次只读 id > 101 的增量
                     生成新摘要 → 推进游标到 103
```

游标记录"摘要已经覆盖到哪条消息"。每次压缩只处理游标之后的新消息，再把旧摘要作为上下文传进去，形成**滚动归纳**。

这套机制要成立，需要满足三个条件：

- **游标只在摘要生成成功后推进**，失败则保留旧值，下一轮重试；
- **摘要与游标在同一事务/同一逻辑单元内更新**，避免"摘要新了、游标没动"或反之；
- **删除消息时要检查是否触及摘要覆盖区**，若触及则清空摘要，防止摘要描述的是已不存在的历史。

#### 5.5、替换语义：摘要是一等公民

压缩之后，下一轮请求到底长什么样？常见有两种做法：

- **替换**：用摘要替换掉被覆盖的早期消息；
- **追加**：把摘要追加到系统指令，历史仍从某个游标之后读取。

两者可以结合。以"摘要 + 增量"为例：

```
本轮请求的历史部分
  = 系统指令（内含摘要）
  + summary_last_message_id 之后的全部消息
```

这样做的关键点是：**摘要成为上下文中的一等公民**，而不是一条普通的 assistant 消息。它跟着系统指令走，拥有更高的注意力权重，也不会被后续消息挤出窗口。

同时，原始消息仍然留在数据库里。摘要只是"请求视图"的一次投影，随时可以重新生成、人工修正，或者在被删除时失效。

#### 5.6、失效与一致性：压缩最容易出事的地方

压缩不是一次孤立的模型调用，它要和会话的增删改并发打交道。工程上至少要处理四类情况：

| 场景 | 风险 | 处理方式 |
| --- | --- | --- |
| 摘要生成失败 | 旧摘要与新历史不一致 | 保留旧摘要与游标，下一轮重试 |
| 删除消息触及覆盖区 | 摘要描述了已删除内容 | 清空摘要，等待重新生成 |
| 同一会话并发压缩 | 重复调用、游标错乱 | 会话级单飞（single-flight）去重 |
| 压缩后运行时仍用旧上下文 | 新摘要下一轮不生效 | 推进游标后清理/重建会话运行时 |

其中"清理运行时"容易被忽略：很多 Agent 会在会话创建时把系统指令固化进运行时对象，如果只更新了数据库里的摘要，运行时仍然拿着旧提示词，就会出现"摘要生成了但模型没看到"的诡异现象。

#### 5.7、异步：生成与消费解耦

压缩要调模型，天然有延迟。如果放在对话主链路里同步执行，用户会明显感到"这一轮特别慢"，甚至因为压缩失败而阻塞回复。

更稳妥的架构是**生成与消费解耦**：

```
对话主链路：读取已有摘要 → 装配 → 生成回复 → 落库
                          ↑
后台链路：本轮结束后 → 判断是否压缩 → 调模型生成 → 更新摘要/游标
```

对话只负责"读"，压缩负责"写"，写失败不影响本轮回复，写成功下一轮生效。这条原则与长期记忆的异步归档是同构的：**任何需要额外模型调用的上下文维护，都不应该阻塞用户等待的那条链路**。

#### 5.8、摘要的边界：它是会话状态，不是长期记忆

摘要解决的是**单个会话内**的上下文收敛；长期记忆解决的是**跨会话**的项目级/用户级沉淀。两者长得很像，但边界必须清楚：

- **作用域**：摘要属于会话，记忆属于项目或用户；
- **内容**：摘要偏"这次任务做到哪了"，记忆偏"这个项目/用户长期成立的事实与偏好"；
- **生命周期**：摘要随会话删除而消失，记忆跨会话持续；
- **触发**：摘要看窗口使用率与轮次，记忆看时间窗口与新消息。

把两者混在一起，常见后果是：会话摘要污染了长期记忆，或者长期记忆被塞进每一轮摘要，越压越臃肿。

### 6、上下文工程：每轮往窗口里放什么

#### 6.1、装配顺序：稳定前缀，动态后置

一个典型的装配顺序如下：

```
┌─────────────────────────────────────────────┐
│ ① 系统指令（Agent 角色、行为约束）          │  ← 稳定
│ ② 长期记忆（项目/用户事实与偏好）           │  ← 低频变化
│ ③ 会话摘要（本次任务进展）                  │  ← 压缩时变化
│ ④ 技能索引 / 工具说明（名称 + 一行描述）    │  ← 稳定
│ ⑤ 增量历史（摘要游标之后的消息）            │  ← 每轮增长
│ ⑥ 检索结果 / 当前用户输入                   │  ← 每轮变化
└─────────────────────────────────────────────┘
```

这个顺序同时服务三个目标：

- **注意力**：最重要的约束放在前面，近期对话放在后面，符合模型对首尾更敏感的特性；
- **缓存**：稳定的前缀有利于 prompt caching，动态内容后置，减少缓存失效；
- **可维护**：每一层职责清晰，出问题能快速定位是记忆、摘要还是检索的锅。

#### 6.2、预算分配：给每一层留多少

没有万能比例，但可以给一个可操作的起点：

| 组成 | 建议占比 | 说明 |
| --- | --- | --- |
| 系统指令 + 工具定义 | 10% ~ 20% | 工具越多越高，必要时做工具裁剪 |
| 长期记忆 + 摘要 | 5% ~ 15% | 定长控制，避免无界增长 |
| 历史增量 | 30% ~ 50% | 压缩的主要调节对象 |
| 检索 / 当前输入 | 10% ~ 20% | 按任务需要动态调整 |
| 输出预留 + 安全边际 | 15% ~ 25% | 不能省，否则容易超窗 |

真实系统里，最不可控的往往是**工具结果**：一次 `cat` 大文件、一次全量日志、一次网页抓取，就可能吃掉一半预算。因此预算治理的重点，通常不是"少放几条历史"，而是"管住工具输出"。

#### 6.3、冲突消解：谁的话更算数

上下文里同时存在系统指令、长期记忆、会话摘要、检索资料和用户当前表述，它们可能互相矛盾。必须有明确的优先级：

```
系统安全约束 > 用户当前明确指令 > 会话摘要 > 长期记忆 > 检索资料
```

尤其要防"记忆反噬"：长期记忆可能已经过时，用户当前说法才是最新的。因此注入记忆时通常会加一句护栏：

> 以下是可能过时的历史事实；若与用户当前表述冲突，以当前表述为准。

这句话成本极低，却能显著降低"Agent 拿着旧记忆跟用户抬杠"的概率。

#### 6.4、工具结果治理：上下文膨胀的最大来源

工具结果治理有几个立竿见影的手段：

- **截断**：只保留头尾与关键行，中间用省略标记；
- **摘要**：让模型先总结工具输出，再决定是否入上下文；
- **卸载**：大结果写入文件，上下文只留路径与摘要，需要时再读；
- **去重**：同一文件多次读取、同一命令多次执行，只保留最新或差异；
- **结构化**：把日志/JSON 提取成字段，而不是整段原文。

在编码 Agent 里，"卸载 + 按需读取"尤其重要：模型不需要一次性看到整个仓库，它需要知道**去哪里找**。

#### 6.5、子 Agent：用隔离换干净

子 Agent（subagent）本质上是一种上下文隔离手段：

```
主 Agent 上下文
  └─ 派生子 Agent（独立上下文）
        ├─ 只带任务说明与必要资料
        ├─ 在自己的窗口里搜索、试错、读文件
        └─ 只回传结论摘要
```

好处是主上下文不被中间过程污染，坏处是子 Agent 可能丢失主对话里的隐含约束。因此任务说明要写清楚目标、边界与输出格式，而不是一句"你去看看"。

#### 6.6、装配 checklist

每次改上下文逻辑，可以用这份清单自查：

- [ ] 系统指令是否稳定？有没有把每轮都变的内容塞进前缀？
- [ ] 记忆/摘要是否定长？有没有无界增长的可能？
- [ ] 历史是否从游标之后读取？有没有重复拼接旧消息？
- [ ] thinking 与工具原始结果是否被过滤或卸载？
- [ ] 检索结果是否有条数/字数上限？
- [ ] 冲突时优先级是否明确？
- [ ] 输出预留是否足够？token 估算是否留了安全边际？

### 7、XXL-AI 落地：一套可运行的会话压缩实现

下面以 XXL-AI 本地版为例，看这套坐标系如何落到代码与数据表上。

#### 7.1、整体链路

```
用户输入
   │
   ▼
chatService.sendChat
   │  ① 校验会话绑定的项目 / Agent
   │  ② 组装系统指令：Agent 指令 + 长期记忆 + 会话摘要 + SKILL 索引 + 约束
   │  ③ 读取历史：summary_last_message_id 之后的增量消息
   ▼
runtimeHost → 会话级 Agent（Pi 运行时）
   │
   ▼
LLM 流式生成 → desk_message 落库
   │
   ▼
本轮结束 → maybeCompressSession（异步）
   │  命中条件：无摘要 / 使用率 ≥ 80% / 用户轮次 ≥ 20
   │  输入：旧摘要 + 增量转录（≤ 60k，排除 thinking 与工具结果）
   │  输出：五段式摘要（≤ 2000 字符）
   ▼
推进 summary_last_message_id → 清理会话运行时 → 下一轮生效
```

链路里有三个关键设计：**摘要进系统指令**、**历史按游标增量读取**、**压缩异步且失败不阻塞**。

#### 7.2、会话压缩：参数与流程

XXL-AI 本地版把摘要存在 `desk_session` 上：

```
desk_session
  summary                  摘要正文（定长 2000 字符）
  summary_last_message_id  摘要覆盖到的最后一条消息 ID
  summary_update_time      摘要更新时间
```

每轮对话结束调用 `maybeCompressSession`，满足任一条件才真正压缩：

- 无摘要；
- 上下文使用率 ≥ 80%；
- 距上次摘要后真实用户轮次 ≥ 20。

压缩输入是"旧摘要 + 增量转录"，其中转录只取用户与助手正文，排除 thinking 与工具结果，上限 60k 字符，超长从最旧处截断。输出固定五个二级标题：

```
## 背景与约束
## 目标
## 关键决策
## 进展与产物
## 待办与风险
```

并截断到 2000 字符。生成成功后推进游标、清理该会话运行时，使新摘要下一轮生效；失败则保留旧摘要与游标，下一轮继续尝试。

删除消息如果触及摘要覆盖区，摘要会自动清空，避免"摘要描述的历史已经不存在"。

#### 7.3、上下文装配：摘要 + 增量 + 兜底

装配时，系统指令由多部分组成：

```
Agent.systemPrompt
  + 长期记忆（项目记忆开启时）
  + 会话摘要
  + SKILL 索引（只有名称与一行描述）
  + 模式 / 工具约束
```

历史消息则从 `summary_last_message_id` 之后读取，形成"摘要 + 增量"的组合。没有摘要时，按最近 50 条 / 12 万字符兜底，保证新会话也能正常工作。

这里有两个值得借鉴的工程细节：

- **技能索引只放名称与描述，正文按需读取**。常驻上下文只放"目录"，避免把大量技能文档塞进每一轮；
- **系统指令在会话 Agent 创建时固化**。因此摘要或记忆更新后，需要清理对应会话运行时（evict），下一轮重新装配；否则模型仍在使用旧提示词。

> 云版的装配顺序是「系统指令 → 短期记忆 → 长期记忆 → 工具 → 知识」，本地版则把摘要与记忆收进系统指令、历史按游标读取。顺序略有差异，但"稳定前缀 + 动态后置 + 按预算裁剪"的原则一致。

#### 7.4、与长期记忆的分层

XXL-AI 把上下文管理拆成两层，边界很清楚：

| 维度 | 会话压缩 | 长期记忆 |
| --- | --- | --- |
| 作用域 | 单个会话 | 项目级（本地版） |
| 存储 | `desk_session.summary` | `desk_project.memory` |
| 触发 | 无摘要 / 使用率 ≥ 80% / 轮次 ≥ 20 | 记忆为空 / 距上次生成 > 5 分钟 |
| 游标 | `summary_last_message_id` | `memory_last_time`（时间游标） |
| 结构 | 背景 / 目标 / 决策 / 进展 / 风险 | 用户偏好 / 项目事实 / 决策 / 待办 |
| 注入 | 系统指令中的会话摘要 | 系统指令末尾的项目记忆 |
| 失败策略 | 保留旧摘要，下一轮重试 | 保留旧记忆，游标不推进 |

两者都遵循同一条铁律：**生成与消费解耦**。对话只读已有结果，压缩与记忆生成在后台异步完成，绝不阻塞本轮回复。

#### 7.5、可观测与排障

上下文系统出问题时，最怕"看不见"。XXL-AI 在开发者模式下提供模型通讯 trace，可以对比压缩前后的请求：

- 本轮实际发送了哪些消息、多少 token；
- 摘要是否被注入、注入在哪一段；
- 工具结果占用了多少预算；
- 压缩是否触发、失败原因是什么。

没有这层可观测性，调参与排障基本只能靠猜。

### 8、权衡与展望

上下文工程没有"正确解"，只有"当前约束下的取舍"。几个必须正视的代价：

- **摘要漂移**：模型每次归纳都可能改变措辞、遗漏约束，甚至把推测写成事实。固定 schema、低温度、定长截断只能缓解，不能根治；
- **有损遗忘**：2000 字符的摘要意味着旧进展会被不断覆盖，这是"滚动窗口式遗忘"的必然结果，需要产品层面接受；
- **触发阈值**：压得太早浪费调用、丢细节；压得太晚可能超窗。80% 与 20 轮只是经验值，应该按模型窗口与业务场景调整；
- **一致性成本**：删除、编辑、并发压缩都会让摘要与历史产生分歧，需要游标、单飞、失效清理等一整套机制；
- **缓存与延迟**：摘要变化会打破 prompt cache，evict 重建也会带来首轮延迟，需要在前缀稳定性与即时生效之间权衡。

评估上，不能只看"省了多少 token"，还要看：

- 压缩后的任务成功率是否下降；
- 关键约束、决策、待办是否被保留；
- 长会话回归用例是否通过；
- 压缩失败率、平均压缩耗时、首 token 延迟是否可接受。

展望几个方向：

- **分层压缩**：会话级摘要之上再做项目级摘要，形成多粒度上下文；
- **重要性感知**：不再简单按时间或定长截断，而是按约束强度、任务相关性决定去留；
- **缓存友好压缩**：尽量把变化收敛到上下文尾部，减少前缀失效；
- **压缩可观测**：把"压了什么、丢了什么、为什么"变成可查询的指标；
- **记忆与压缩统一**：会话摘要、长期记忆、知识检索共用一套预算与冲突消解框架，而不是各自为政。

### 9、结语

上下文窗口不是免费的午餐，而是一种**稀缺的、需要调度的工作内存**。

会话给它一个结构，压缩给它一个收敛机制，上下文工程决定每一轮到底把哪些 token 放进去。三者合起来，才构成一个能在长对话、长任务中保持稳定的 Agent。

如果只用一句话记住本文：

> **会话决定记住什么，压缩决定忘掉什么，上下文工程决定这一刻看什么。**
